# Changelog

Versions of the buzz-agent-team skill, newest first. The version is the one line of `buzz-agent-team/VERSION`, and each one is the Git tag `v<version>` of this repository. What the three numbers mean is in the [README](README.md#versions).

## 5.4.1 (2026-11-24)

The assistant checks the launcher at the start of every use of the skill. Only `SKILL.md` and the documents change: no script, no template and no team file.

- **A rule of its own.** In 5.4.0 the instruction to keep the launcher on `PATH` level with the skill sat inside step 1 of the setup flow, so an assistant that only upgraded, started or checked a team met it late or not at all. It is now one of the Rules: before anything else in every use of the skill, run `agent-team.sh launcher --dry-run`; when it would install or replace, say so in one line and run `agent-team.sh launcher`; when the same file is there, go on without a word.
- **A leftover sentence is gone.** Step 1 still told the assistant to ask the user to confirm "the accepted launcher". It now says what the `launcher` line of a passed preflight reads: `(the one this skill brings)`.
- What the script does is unchanged from 5.4.0: `preflight`, `status`, `create` and `upgrade` compare and report, and only `agent-team.sh launcher` writes. A team's own command, `team.sh`, still does not compare: it knows no skill.

- **One test read the launcher from its old place.** `test-team-sh.sh` compared the team command's list of credential names with the launcher in a Buzz checkout, `local/buzz-acp/run-buzz-acp.sh`, which holds only a pointer since the launcher moved. It now reads the skill's own launcher, and fails when that function is not found instead of skipping.

Checked: both suites; the `SKILL.md` scenario of `test-agent-team.sh` now requires the rule's two phrases.

## 5.4.0 (2026-11-24)

The launcher comes with the skill. `run-buzz-acp.sh`, the program that starts one agent, changes together with the skill, so the skill now carries the copy that fits it and one command puts it on `PATH`. No team file changes: a team made by 5.3.0 needs no upgrade for this.

What a 5.3.0 user sees change, after the skill is installed:

- **`scripts/run-buzz-acp.sh` is in the skill folder.** In this version it is, byte for byte, the launcher that was kept in a Buzz checkout as `local/buzz-acp/run-buzz-acp.sh` (sha256 `4683b969…`). From now on the skill's copy is the one that is changed and released.
- **`agent-team.sh launcher`** puts it where a start finds it. It replaces the `run-buzz-acp.sh` that `PATH` finds now; when there is none, it installs it into `~/.local/bin`, mode 700, and says so when that folder is not on `PATH`. `--dir DIR` names another folder, and `--dry-run` says what would change.
- **The earlier file is kept** beside the new one as `run-buzz-acp.sh.bak-<UTC time>`. A file that is already the same is left as it is, and a symbolic link is refused.
- **Agents that already run are not affected.** The launcher has become the harness by then. The new file is written beside its place and moved into it in one step.
- **The skill says when the launcher is another one.** `preflight` shows `launcher ... (the one this skill brings)`, or a `note` line with `agent-team.sh launcher` as its fix; a launcher that is not found is `MISSING` with the same fix, where it used to ask for a path. `status` says it on its `Launcher for start` line, and `create` and `upgrade` end with one line that starts `Launcher:`. None of them writes the launcher.
- **The assistant keeps it current.** `SKILL.md` tells Claude or Codex to run `agent-team.sh launcher`, dry run first, whenever one of those lines appears, and to say what was replaced.
- **`settings --launcher` and `AGENT_TEAM_LAUNCHER` still work** and win for this skill's own `start`; a team's own command uses the one on `PATH`. `agent-team.sh launcher` notes it when they name another file.
- `install.sh` requires `scripts/run-buzz-acp.sh`. The two offline suites now run their real-launcher checks with the skill's own launcher by default; `AGENT_TEAM_REAL_LAUNCHER` names another one.

What was measured and what was only read:

- **Measured, offline:** the scenario "the launcher this skill brings" of `test-agent-team.sh`, in a home folder and on a `PATH` of the test: none on `PATH`, the same file, another file, a symbolic link, another folder, the three states in `preflight`, and the lines of `status`, `create` and `upgrade`.
- **Measured on the owner's machine:** the launcher on `PATH` there was already the same file, so `agent-team.sh launcher` changed nothing.
- **Not measured:** a start of a real agent with a launcher this command has just replaced.

## 5.3.0 (2026-11-24)

The channel supervisor listens in every channel it is a member of. Before, an ordinary message started its turn without a mention only in the channel its team was set up for; anywhere else it needed a mention. The team folder format does not change: a team made by 5.2.0 keeps starting as it is, and gets this after `agent-team.sh upgrade <team>`.

What a 5.2.0 user sees change, after `agent-team.sh upgrade <team>` and a restart of the channel supervisor:

- **An ordinary message in any channel the channel supervisor is a member of starts its turn,** from anyone who can post there, without a mention. A direct mention still does, as before. Membership is the switch: to keep it out of a channel's talk, do not add it to that channel.
- **Nothing else about it changes.** It still acts only on a message signed by you, a rule in its prompt that nothing enforces, and it now meets more people: in every channel it is in, anyone's message reaches it with every tool call approved. It still takes no turn for its own team's agents.
- **It takes no turn for any local agent unless that agent mentions it.** The rule without a mention used to name the local agents of its team's channel. It now names every agent under `~/.buzz-agents`, whatever channel each team was made for, because any two of them may share a channel.
- **The workspace agent and the reviewer do not change.** Each still takes a turn only when it is mentioned.
- **Cost.** The channel supervisor takes a model turn on every ordinary message in each of those channels, also when it then stays silent.
- **Two channel supervisors in one channel both answer a person's message there.** Neither takes a turn for the other's message, once both are upgraded.
- **Its prompt says so.** A new paragraph tells it that it hears every channel it is a member of, and to hand work to the workspace agent in a channel that agent is in. Like the rest of the prompt, it names no channel.
- **Shown.** `team.sh check` and `status` say `answers anyone in the channels it is a member of`.

How the upgrade does it:

- With the agents stopped, `agent-team.sh upgrade <team> --dry-run` names, for the channel supervisor, `subscriptions.toml`, `prompt.md` and `.env.buzz-acp.local` (one comment line) as replaced, each kept beside itself as `<file>.bak-<UTC time>`, then `team.sh: replace` and `VERSION: 5.2.0 -> 5.3.0`. A team without a channel supervisor gets only the team command and the version.
- In `subscriptions.toml` the first rule is now called "Channel discussion" and has `channels = "all"`, where it named the one channel, and its filter names every local agent.
- **Upgrade every team that has a channel supervisor** when a team gets new agents: `create` now names each of them, not only those of the same channel. Until then that channel supervisor takes turns for the new agents' ordinary messages in a channel they share.
- A prompt you edited by hand is replaced like any generated file; the earlier one is kept as `prompt.md.bak-<UTC time>`.

What was measured and what was only read:

- **Measured, offline:** the generated rules, run through the test's own reading of the harness's matching order (channel, kind, mention, author filter): an ordinary message in the team's channel and in another channel starts a turn; a local agent of another team, made for another channel, starts none without a mention and one with a mention; the team's own agents start none either way.
- **Read in the harness source** (`crates/buzz-acp/src/config.rs` and `filter.rs`): a rule with `channels = "all"` applies to every channel the agent has discovered, which are the channels it is a member of, and one rule without `require_mention` makes that channel's subscription deliver ordinary messages.
- **Not measured:** a real channel supervisor taking a turn in a second channel. An agent that is not local, such as one Buzz Desktop runs, is in no filter: its ordinary messages start the channel supervisor's turn, as they already did in its own channel.

## 5.2.0 (2026-11-24)

A restart: an agent starts again as its last run was, with nothing asked and no choice changed. The team folder format does not change: a team made by 5.1.0 keeps starting as it is, and gets the restart after `agent-team.sh upgrade <team>`.

What a 5.1.0 user sees change, after `agent-team.sh upgrade <team>`:

- **`restart.sh` in each agent folder,** beside `start.sh`: `~/.buzz-agents/<team>/<agent>/restart.sh`. It starts that agent again as its last run was: the provider, the model, the reasoning effort, the project folder and, for the workspace agent, the model and the reasoning effort of its workers. They are those of the last run, whatever is saved in `agent.conf` and whatever folder the command is run from, so it needs no `cd`. It asks nothing, in a terminal too.
- **`team.sh restart`** does the same for the team. Without a name it takes the agents that run now and those that ended by themselves, and leaves a stopped one stopped. `team.sh restart <agent>...` takes those agents, running or stopped, and `team.sh restart --all` every agent with a run on record.
- **No option changes a choice.** `--force` ends an agent that does not stop in time, as for `stop`, and `--verbose` prints the launcher's own check. Any other option is refused with the way to change a choice: stop the agent, then start it with `start.sh` and the option.
- **A stop keeps the record of the run.** `agent.pid` holds the choices of a run. `team.sh stop` now keeps that file as `agent.last` in the agent folder instead of removing it, and a start removes `agent.last`, because the run it starts is the last one then. The skill's own `agent-team.sh stop` and `start` do the same. So a stopped agent can be started again as it last ran.
- **Across an upgrade.** An upgrade carries `agent.last` over with the rest of the agent folder. The agents come back as they ran with three commands: `team.sh stop`, `agent-team.sh upgrade <team>`, `team.sh restart --all`. A model that the upgrade saves does not change that: a restart repeats the last run, and `start.sh --yes` starts on the saved choices.
- **Status** prints one more line per agent: `restart it as it runs: <agent folder>/restart.sh` for an agent that runs, and `start it again as it last ran (<provider, model, effort, project folder>): <agent folder>/restart.sh` for one that is down with a run on record.
- **The agent's log** names a restart as `team.sh restart (...)`, where a start says `team.sh start (...)`.

How a restart works:

- It reads the record of each agent's last run and hands it to the start as the options that would give that run. So every check of a start applies, and a recorded choice that is refused now stops it before anything is stopped: a model the provider no longer offers, a project folder that is gone, a record that does not name its provider. The message then ends with `Nothing was stopped: each agent is as it was.`
- **An agent that runs is stopped before the check.** The launcher holds a lock for each running agent and refuses to check one that runs, so a restart cannot check first. The agent is down for the stop, the check and the start.
- **A failure after the stop leaves every record in place.** When the check fails, nothing starts, each agent keeps the record of its last run as `agent.last`, and the message names the command that starts them again, `team.sh restart <the same agents>`. When one agent ends right after starting, the other agents of the restart are still started; the failed run stays on record in its `agent.pid`, and its own `restart.sh` starts it again.
- **An agent that does not stop in time** stays as it is and is named at the end; the others are restarted. `--force` ends it.
- **Two things follow the project folder as it is now,** not the last run. An agent gets the browser when the file of its provider names it now: a restart writes nothing for the browser, and says so when that differs from the last run. And the settings of its provider (the sandbox settings on Claude, the buzz rule on Codex) are put into the project folder again, unless the last run had none (`--no-wall`).

How the upgrade does it:

- With the agents stopped, `agent-team.sh upgrade <team> --dry-run` names `<agent>/restart.sh: add` for each agent, `team.sh: replace` and `VERSION: 5.1.0 -> 5.2.0`. No env file, prompt or record changes. A second run says it is up to date.
- **Stop a 5.1.0 team with the skill's own stop, and nothing has to be chosen again.** The `team.sh` of 5.1.0 removes each record when it stops an agent; `agent-team.sh stop <team>` of this version keeps it. So for a team whose agents run: `agent-team.sh stop <team>`, `agent-team.sh upgrade <team>`, then `<team folder>/team.sh restart --all`, and every agent runs again as it ran before.
- **A team that was stopped by its own 5.1.0 `team.sh` has no records.** Start each agent once with its `start.sh`; from then on `restart.sh` works, and so does `team.sh restart --all` after a stop.
- `create` puts `restart.sh` into each agent folder of a new team, and `install.sh` requires `templates/agent-restart.sh`.

What was measured and what was only read:

- **Measured, offline:** the scenario "restart" of `test-team-sh.sh`, with stand-ins for the launcher, the harness and the adapters. Its stand-in launcher refuses to check an agent that runs, as the real one does, and a check of two running agents fails there while their restart passes. It covers a running agent, a stopped one, a run without the sandbox settings, both agents across an upgrade that saves another model, each agent's own `restart.sh` from another folder, the refused options, each failure above, and the way to this version for a team made by 5.1.0 (the skill's own stop, the upgrade, `restart --all`).
- **Read in the launcher,** `run-buzz-acp.sh`: `--check` ends with "a run would be refused" when the agent's lock is held by a live process.
- **Not measured:** a restart of a real agent with the real launcher.

## 5.1.0 (2026-11-24)

Three things: a live view for you in Buzz Desktop, parallel conversations for the channel supervisor, and the newest models again for agents on Codex. The team folder format does not change: a team made by 5.0.0 keeps starting as it is, and gets all three after `agent-team.sh upgrade <team>`.

What a 5.0.0 user sees change, after `agent-team.sh upgrade <team>`:

- **The live view.** Buzz Desktop shows you what each agent does, and you can cancel a turn or switch its model from there. The harness publishes the agent's activity as frames encrypted to you, and takes three controls back, from you only: cancel a turn, switch the model, publish project announcements. It finds your public key in the agent's stored proof. Every env file gets `BUZZ_ACP_RELAY_OBSERVER=true`, with a comment line. Buzz Desktop switches it on for the agents it creates.
- **The live view is the team's choice.** `team.conf` saves it as `observer=yes` or `observer=no`; a team without the line has it on. `create` and `upgrade` take `--observer` and `--no-observer`. With it off, the env files say `BUZZ_ACP_RELAY_OBSERVER=false`.
- **The channel supervisor runs 3 conversations at a time.** The harness runs as many adapter processes as `BUZZ_ACP_AGENTS` says. With one, a turn waits until the turn before it ends, also when the two are in different conversations; with three, turns for different conversations run at the same time. The channel supervisor's env file says `BUZZ_ACP_AGENTS=3`, and its `agent.conf` saves it as `parallel=3`. `create` and `upgrade` take `--supervisor-parallel N`, from 1 to 8. Buzz Desktop uses 10.
- **The workspace agent and the reviewer run one conversation at a time,** with no option. The workspace agent must not run two jobs on the same files at once, and the reviewer is only mentioned now and then. Their env files say `BUZZ_ACP_AGENTS=1`.
- **Shown.** `team.sh check` and `status` print one `live view` line per agent: on, with what it does, or off, with the option that changes it. `team.sh` reads it from `team.conf`, not from the env files. For the channel supervisor they print one `conversations` line, `3 conversations at a time: three adapter processes`, and the line that says it started names it too. An agent is still one process: `agent.pid`, `stop` and `status` follow the harness, which starts and stops its adapter processes itself.
- **Agents on Codex can use the newest models again.** The stock adapter, `codex-acp` 1.13.1, runs the Codex CLI it bundles, Codex 0.156.1, unless `CODEX_PATH` names another program. That Codex lists `gpt-6.2-astra`, but cannot run it with a ChatGPT sign-in. So `team.sh` now starts each agent on Codex with `CODEX_PATH` set to `~/.local/share/buzz-agent-team/node_modules/.bin/codex` when that file is there and your shell has no `CODEX_PATH` of its own. A `CODEX_PATH` of your shell is left as it is and wins. `agent-team.sh start` does the same. Model lists and menus are retrieved with the same Codex the agent will run: in `team.sh`, and in `agent-team.sh models`, `create`, `upgrade` and `start`. `AGENT_TEAM_CODEX_CLI` names another file; `none` means the adapter's own.
- **One `codex` line per agent on Codex** in `team.sh check`: the program the adapter will run, its version and where the choice comes from, `~/.local/share/buzz-agent-team`, your shell's `CODEX_PATH`, or the adapter's own. The adapter's own is a note, not a problem: a turn on one of the newest models then fails without a line in the log. The note gives the one line that installs a newer Codex: `npm install --prefix "$HOME/.local/share/buzz-agent-team" --save-exact @openai/codex@0.171.0`. `preflight` prints the same line for a role on Codex, with the install line as its fix.
- **The adapter stays 1.13.1.** Adapter 2.10.0 bundles Codex 0.171.0, but the harness cannot talk to it, and the launcher refuses any adapter but 1.13.1.
- **Correction: keep `~/.local/share/buzz-agent-team`.** The 5.0.0 entry, the README and `SKILL.md` said you may delete it. That was wrong: its Codex 0.171.0 is the one agents on Codex need for the newest models.
- `test-codex-adapter.py` drives the Codex CLI that `AGENT_TEAM_CODEX_CLI` names, so its two live checks can be run for adapter 1.13.1 with a newer Codex. Without it, it drives the adapter's own, and each result line names the Codex it drove.

How the upgrade does it:

- With the agents stopped, `agent-team.sh upgrade <team> --dry-run` prints the plan. For a team made by 5.0.0 it names, for each agent, `live view: off -> on (BUZZ_ACP_RELAY_OBSERVER=true)`, and for the channel supervisor `conversations at a time: 1 -> 3 (BUZZ_ACP_AGENTS=3: three adapter processes)`. It names the files it replaces (each env file, and the channel supervisor's `agent.conf`), `team.conf: observer=yes`, the team's files and `VERSION: 5.0.0 -> 5.1.0`.
- It writes `observer=` into `team.conf` first, so that the next run finishes an upgrade cut short with the same choice. Then it rebuilds each agent folder as before: the env files get the new lines, and keep everything else as an upgrade keeps it. Then it replaces the team's files and writes `VERSION` last. A second run says it is up to date.
- A team made by an earlier format goes straight to 5.1.0, in the same run.

What was measured and what was only read:

- **Measured on 2026-11-24, on the owner's machine, before this release was built.** Adapter 1.13.1 bundles Codex 0.156.1. That Codex lists `gpt-6.2-astra`, without effort levels, but every turn on it ends with `The 'gpt-6.2-astra' model is not supported when using Codex with a ChatGPT account` (HTTP 400); the start check passes, `team.sh status` says running, and the harness log records nothing. Adapter 1.13.1 with Codex 0.171.0 passes both live checks of `test-codex-adapter.py`; `buzz-acp models --agent-command codex-acp --agent-args ""` then lists `gpt-6.2-astra` with every effort level, and a real request on that model is answered. Adapter 2.10.0 passes the two live checks too, but `buzz-acp models` with it fails with `Agent reported error (code -32602): Invalid params`.
- **Measured for this release:** the two live checks of `test-codex-adapter.py` (`--also-browser --also-buzz-rule`) passed with adapter 1.13.1 and its own Codex 0.156.1, and again with Codex 0.171.0 named by `AGENT_TEAM_CODEX_CLI`. The offline suites check the lines the skill writes, saves and shows, the upgrade from 5.0.0, and where `CODEX_PATH` is set, with stand-ins for the launcher, the harness and the adapters.
- **Only read:** everything about the live view and the parallel processes. They are harness settings, `BUZZ_ACP_RELAY_OBSERVER` and `BUZZ_ACP_AGENTS`, read in its source (`crates/buzz-acp/src/config.rs` and `lib.rs`), and that the launcher passes both lines of an env file to the harness was read in `run-buzz-acp.sh`. Whether Buzz Desktop shows the live view for an agent it did not create was not tested.

## 5.0.0 (2026-11-24)

Every agent runs on the stock adapter, as the workspace agent does. The channel supervisor and the reviewer no longer run the restricted runtime, a fixed list of read-only tools, which kept them from ordinary work: they could not look at a picture posted in Buzz, use your connected services or run anything, and they asked the workspace agent for small things. What each agent may do is now a rule in its prompt, as it already was for the workspace agent. A team made by 4.x does not start until it is upgraded (team folder format 5).

What a 4.3.0 user sees change, after `agent-team.sh upgrade <team>`:

- **Every agent has every tool of its adapter.** The env files of the channel supervisor and the reviewer name the stock adapter (`claude-agent-acp` or `codex-acp`) and `BUZZ_ACP_PERMISSION_MODE=bypass-permissions`, as the workspace agent's do. Whom each agent answers and when it takes a turn do not change: the channel supervisor answers anyone in its channel, by `subscriptions.toml`; the reviewer answers anyone who mentions it; the workspace agent answers you and its channel supervisor.
- **What the channel supervisor can do now.** For anyone in its channel it reads the project, looks something up, looks at a picture or a page, and answers. For you alone, on a message signed by you, it acts: it changes a file, runs a command that changes something, uses a connected service such as a tracker, and creates or changes a channel, now with the Buzz CLI (`buzz channels`). It does small things itself and hands the workspace agent the work that changes several files, runs for long or needs workers. Its prompt is new: "Who you act for", "What you do yourself and what you hand over", "Pictures in messages", "Channels" and "Your workspace", the workspace agent's rule word for word.
- **What the reviewer can do now.** It reads, runs checks such as the project's tests, looks at a picture or a page, and looks something up, for anyone who asks it for a review. Its prompt tells it never to change the work it reviews. Its prompt gets "Pictures in messages" and "Your workspace".
- **The workspace agent's prompt** says that the channel supervisor works in the same project folder and may make a small change you asked it for, and gets "Pictures in messages": a picture someone posts reaches an agent as a link, which it saves into the project folder with `buzz media get <link> --output .buzz-media/<name>` to look at it.
- **What holds each agent is the same for all of them:** the sandbox settings on Claude, `.claude/settings.json` in the project folder, and Codex's workspace-write sandbox on Codex, with `INITIAL_AGENT_MODE=agent`. All agents of a team work in the same project folder, so these settings hold all of them. `team.sh` does at each start for every agent what it did for the workspace agent: the settings, the mode pin, the clean-up of the environment, the model and the effort. The workers' questions and options stay the workspace agent's.
- **The buzz rule on Codex.** In Codex's sandbox a command has no network, and an agent posts to Buzz with the `buzz` command. So for an agent on Codex, `workspace-settings.py` now keeps `.codex/rules/buzz.rules` in the project folder: one line, `prefix_rule(pattern = ["buzz"], decision = "allow")`. With it a plain `buzz` command runs with the network and goes to no reviewer. A line that combines `buzz` with anything else stays in the sandbox, without the network. `workspace-settings.py apply|check [claude|codex] PROJECT_FOLDER` (`claude` when the word is left out) writes, completes or checks it: an existing file keeps what it holds, the line is added at its end, and the earlier file is kept beside it as `buzz.rules.bak-<UTC time>`; a symbolic link (the file, `.codex/` or `.codex/rules/`) or a file that cannot be read as text is left alone. `team.sh` writes it before a start as it writes the Claude settings: a failure is a PROBLEM line and nothing starts, and it is never written into a project folder the team may not use. `--no-wall` skips it too, and the check then notes that each `buzz` command goes through Codex's own reviewer. `create` and `upgrade` write it when an agent of the team is saved on Codex, and the check prints it on the agent's `sandbox` line. No workspace agent on Codex had it before, so before 5.0.0 its `buzz` commands had no network unless Codex's reviewer let one leave the sandbox.
- **The browser belongs to the project folder.** Every agent now reads the project folder's tool-server file, so every agent started there has the browser when the file of its backend names it. `team.sh start --browser` and `--no-browser`, and each agent's `start.sh`, take the options for any agent. In a terminal a start asks once, after every agent's questions: `A browser for the agents in this project folder (headless Chrome, signed in to nothing)? [y/N]`. The default is yes only when the file of every started agent's backend names it. Yes names it for each of those backends, no takes it out of both files, and Enter keeps each file as it is. Each started agent whose backend's file then names it gets the section "Your browser for this run" in its prompt for that run, `on` in its `agent.pid`, and a `browser` line in the check. `create` and `upgrade` with `--browser` name it for each backend the team's agents are saved on, and a reviewer's own team takes it too. The messages of the fetch at a start name no agent: `Fetching the browser, ...` and `note: the browser tools may be missing in this run: ...`. Everything else of 4.3.0 stays: the helper, the fetch, the notes and the two section texts.
- **Model lists.** Every role uses the models the stock adapter offers. Without a retrieved list, a Codex model is checked against the catalog of the Codex CLI the stock adapter bundles, for every role. A list kept from the restricted runtime (one whose first line names a `runtime/` adapter) is not used, and the next model menu retrieves the stock adapter's.
- **Removed.** `buzz-agent-team/runtime/` (`restricted-claude`, `claude-agent-acp`, `codex-acp`, `buzz-tools`), the code that installed, found, checked and started it, its preflight lines and its requirements (`@openai/codex`, `@modelcontextprotocol/sdk` and `zod` under `~/.local/share/buzz-agent-team`, and Node.js for a channel supervisor or a reviewer), `test-partner-runtime.py`, and `preflight --partner`, which had no effect. `test-codex-partner.py` is now `test-codex-adapter.py`. You may delete `~/.local/share/buzz-agent-team`; the skill does not delete it. (Wrong, and corrected in 5.1.0: keep that folder, whose Codex agents on Codex need for the newest models.)

What is no longer enforced:

- **The channel supervisor answers anyone in its channel, and every tool call is approved without a person** (bypass-permissions). Only its prompt keeps someone else's message from making it act: the rule that it acts only on a message signed by you. Before 5.0.0 its runtime held it to read-only tools whatever a message said.
- **The reviewer can now change files.** Only its prompt says that it does not.
- **Each agent's turn carries the full tool list** of its adapter, the tool servers its project folder names included, as the workspace agent's did.
- Starting work, for the workspace agent, still needs your own accepting message; that is a prompt rule, as before.

How the upgrade does it:

- With the agents stopped, `agent-team.sh upgrade <team> --dry-run` prints the plan. For the channel supervisor and the reviewer it says: `tools: from now on every tool of the stock adapter, in bypass-permissions, as the workspace agent has: it can edit files, run commands and use your connected services. What it may do is a rule in its prompt, which nothing enforces`. It names a saved model the stock adapter does not offer; that model is kept, and a start uses it as saved.
- Each agent folder is rebuilt beside itself and swapped in, as before. ## 4.1.0 (2026-11-23)

The channel supervisor can create and manage Buzz channels, so a channel can be made for a short-lived purpose or for good. The team folder format does not change: a team made by 4.0.0 keeps starting as it is.

- **What the channel supervisor can do.** Its Buzz tools gain `list_channels`, `get_channel`, `list_channel_members`, `create_channel`, `update_channel`, `set_channel_topic`, `set_channel_purpose`, `add_channel_member`, `remove_channel_member`, `archive_channel` and `unarchive_channel`. A new channel is a stream unless the call says forum, and private unless it says open. `ttl_seconds` (60 seconds to one year) makes it temporary: the relay archives it after that long without a message. `update_channel` changes a channel's name, description, visibility or lifetime, and `permanent: true` makes a temporary channel permanent. Each tool runs `buzz channels …` with a fixed argument list, and a name, description, topic or purpose goes as one `--flag=value` argument.
- **What it cannot do.** There is no tool to delete a channel, to leave one, or to change its join role, auto-join or add policy. `add_channel_member` adds a member, a bot or a guest, never an owner or an admin.
- **The reviewer gets none of them.** `runtime/buzz-tools` reads the agent's role from `agent.conf` in its folder and registers the channel tools only for `role=supervisor`. Another role, or a file that is missing or unreadable, gets none. On Codex, `runtime/codex-acp` now enables them; they exist only where `buzz-tools` registers them. On Claude, `runtime/restricted-claude` already allowed the whole `buzz` server and is unchanged.
- **The relay still decides.** The channel supervisor is the owner of the channels it creates, so it can change them. In a channel where it is a member or a bot, as in the project's channel, the relay lets it set the topic and purpose and add people, and refuses the rest: renaming, the description, visibility and lifetime, archiving and removing members. So the project's channel keeps its settings and members unless the owner raises the channel supervisor's role there. (Read in the relay's source, not tested against a relay.)
- **Acting only for the owner is a prompt rule.** A new section of its prompt, "Channels", tells it to create or change a channel only when the owner asks, in a message signed by the owner; to make a channel private unless the owner says open, and temporary when its purpose is short-lived; to add the owner and the people the owner names; and to post the channel's name in the thread. The tools do not enforce any of it, and the channel supervisor listens to anyone in its channel.
- **An existing team.** `agent-team.sh upgrade <team>` puts the new `runtime/buzz-tools`, `runtime/codex-acp` and prompt into it, keeping each earlier file as `<file>.bak-<time>`. Until then its channel supervisor runs with the 4.0.0 tools and prompt.
- **Tests.** `test-codex-partner.py` runs `runtime/buzz-tools` with a recording stand-in for `buzz`, for a channel supervisor, a reviewer, a folder without `agent.conf`, one whose `agent.conf` cannot be read and one whose first `role=` line is not `supervisor`: the tools each one gets, the exact arguments of every call, and the values each tool refuses.
