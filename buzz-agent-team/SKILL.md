# Buzz agent team setup

You guide the user through the whole setup in chat. A bundled script does every step: you run it, show what it printed, and ask the user for what it needs, **one question per message**.

## The team you create

A team has two agents with two jobs: the workspace agent and the channel supervisor. Each has a folder in the team folder `~/.buzz-agents/<name>/`. The workspace agent's folder is named after the team, `<name>` itself (or `agent` when that name is one a team folder uses for something else; `create` says so); the channel supervisor's is `supervisor`. On a command line an agent is named by its folder, and the workspace agent also by `agent`. In options the two roles are `agent` and `supervisor`.

- **The workspace agent** (role `agent`, folder `<name>`) takes the project’s display name. It is the project’s agent in the workspace: a supervisor in subagent mode. It plans the work, dispatches bounded work to worker subagents, reviews their evidence, and keeps `PROJECT.md` and the selected tracker. It runs the stock adapter with all its tools. It takes a turn when the owner or its channel supervisor mentions it, and answers both. It starts workers or changes files only for a bounded run the owner authorized, and it checks that the accepting message is signed by the owner, also when the channel supervisor relays it. Keep the tracker choice specific to the project.
- **The channel supervisor** (role and folder `supervisor`) is named “<Project> Supervisor”. It considers each ordinary message in the setup channel, including messages from other members, and decides whether a reply would help. It runs brainstorms to a decision, proposes todos, and brings decisions to the owner. It hands work the owner accepted to the workspace agent by mentioning it and naming the accepting message. It takes no turn for its own team's agents, so the workspace agent's replies never set it off, and none for other local agents of its channel unless they mention it. In other channels it joins, mentions can start a turn. It can read project files, discuss ideas in Buzz, post proposed todos in the thread, and save its own memory. It can also create Buzz channels, temporary or permanent, change their settings, members and archive state, and set their topic and purpose; it cannot delete a channel. The relay decides what its role in each channel allows: it is the owner of the channels it creates. Its prompt tells it to do this only when the owner asks; its tools do not check who asked. Its harness supplies a limited set of tools: no file edits, no shell, no delegation.
- **Each agent runs on Claude or Codex, with its own model,** and signs in only through the user's subscription: the Claude sign-in or the ChatGPT sign-in. No API key, token or gateway address is ever used; the launcher removes them and refuses to start an agent that would use one.
- **Independent reviewer** (optional, a one-agent team of its own; step 14). It reads the project folder and the Buzz threads and posts its review. Its runtime gives it no file edits, no commands and no web, as for the channel supervisor, and no channel tools. It takes a turn when anyone in its channels mentions it.
- **Whom the workspace agent answers.** Its env file names the channel supervisor's public key; with no channel supervisor known on this machine, it answers the owner only. The harness also lets through any agent whose Buzz profile carries a proof from the same owner. So the channel supervisor, which listens to anyone in the channel, can start a turn of the agent that has every tool. Starting work still needs the owner's own accepting message: that is a rule in its prompt, and the harness does not enforce it. Say this before `create`.
- **What holds each agent to the project folder.** The channel supervisor and the reviewer are held by their restricted runtime. The workspace agent keeps its tools and runs the stock adapter, with nothing in front of it. Two things hold it:
  - **A rule in its prompt:** stay inside the project folder, and run a command outside the sandbox only for a tool installed elsewhere or for network access the task needs.
  - **Sandbox settings.** On Claude they are plain Claude Code settings in the project folder, `.claude/settings.json`, which `create` writes first and `team.sh` writes before a start. Its file tools then read and write only inside the project folder, and its shell commands run in a sandbox that writes only inside the project folder and a temporary folder and reads no user folder outside the project folder. On Codex the stock adapter runs every turn in Codex's workspace-write sandbox by itself, so no file is written: its commands write only inside the project folder and temporary folders, and they can read the whole disk.
  - **What the settings do not hold,** and only the rule asks for: a command the workspace agent runs again outside the sandbox, a `buzz` command given a file outside the project folder, what a workspace agent on Codex reads, and folders the user's own Claude settings add as working folders. Network access is not limited.
  - **The settings file applies to every Claude Code session started in that folder, the user's own included.** Say this before `create`, and say that an existing `.claude/settings.json` keeps everything else it holds, with the earlier file kept beside it.
- Both agents consult the workspace’s `PROJECT.md` and the relevant Buzz threads and worker reports. Each agent has its own relay-backed memory under its identity across joined channels. Share decisions through the project record and respect each conversation’s audience.
- Keep channel IDs, owner keys and local paths in the harness configuration. Use role names and responsibilities in prompts. The setup command names each agent by its folder for identity management.
- **Cost:** every running agent uses the user's own subscription allowance. The channel supervisor takes a model turn on every ordinary message in its channel, even when it then stays silent. Say this before the user starts the agents.

## The script

Everything goes through `scripts/agent-team.sh` in this skill's folder (the folder that holds this `SKILL.md`). Always call it by its full path, in double quotes:

- **Claude Code:** the folder is `${CLAUDE_SKILL_DIR}`, so the script is `"${CLAUDE_SKILL_DIR}/scripts/agent-team.sh"`. Claude Code replaces `${CLAUDE_SKILL_DIR}` with this skill's folder.
- **Codex:** the skills list gives this file's path, ending in `buzz-agent-team/SKILL.md`. The script is `scripts/agent-team.sh` in that same folder.

Below, `agent-team.sh` stands for that full path. `agent-team.sh help` lists every command and option. If running it says "permission denied", the folder was copied without its file modes: ask the user to run `chmod +x` on the script, or to install the skill again.

`agent-team.sh version` prints this skill's version, the one line of `VERSION` in this folder. A team folder keeps the version of the skill that created it or last upgraded it, in its own `VERSION` file: `agent-team.sh status <name>` shows it beside this skill's version, and `team.sh version` prints it. When the two differ, or a team made before version 1.0.0 has none, the dry run of step 13 shows what an upgrade would change.

## The team's own command

Each team folder (`~/.buzz-agents/<name>/`) holds `team.sh`, a copy of this skill's `templates/team.sh`. It checks, starts, stops and reports that folder's agents, and it is what the user runs from then on:

- `team.sh check` verifies the environment and starts nothing: the launcher, `buzz-acp` and `buzz` on `PATH`, each agent's adapter, the project folder, each agent's key, settings file, prompt and proof, and the launcher's own check of each agent with its subscription sign-in.
- **The project folder the agents work in is the folder `team.sh` is run from**, or the one `--workspace <dir>` names. It is never the team folder or a folder around it, because the secret keys are there: run from the team folder, the command uses the project folder saved in `team.conf`.
- `team.sh` (or `team.sh start`) runs that check, then starts. In a terminal it asks which agents to start, then the provider (Claude or Codex), the model and the reasoning effort of each one, and for the workspace agent then the model and the reasoning effort of its workers. Enter keeps the saved choice; a choice lasts for that run.
- `team.sh status` and `team.sh stop` report and stop them. `team.sh help` lists the options.
- **Each agent folder also holds its own start command, `start.sh`** (`~/.buzz-agents/<name>/<agent>/start.sh`, a copy of this skill's `templates/agent-start.sh`). It starts that one agent and no other, through `team.sh`. In a terminal it asks that agent's provider, model and reasoning effort, and for the workspace agent its workers' model and effort; Enter keeps the saved one. `--yes` asks nothing; `--model`, `--backend`, `--effort`, `--worker-model`, `--worker-effort` and `--workspace` set one run, and `--no-wall` starts the workspace agent on Claude without putting the sandbox settings into the project folder. Give it to the user when they want one agent at a time.
- **The model menu shows what the provider offers at that moment.** Before an agent's model menu, `team.sh` asks that provider's adapter for its list with `acp-models.py` from the team folder: one session, no model turn, the user's subscription sign-in, at most 30 seconds. The list replaces the kept one in `models/`. When it cannot be retrieved, the command says why and offers the kept list with its date. A model given by option that the kept list lacks is looked up the same way before it is refused. A start that asks nothing retrieves nothing.
- **A Claude agent is never started or saved with the model `default`.** The Claude adapter's list has that entry, but Claude Code takes it as a model name and refuses every turn, so the agent stays silent. The start menu leaves it out, and `team.sh`, `start.sh`, `create`, `upgrade` and `settings` refuse it. For the runtime default, save no model.

It finds everything from its own location and names no skill, so a team folder runs without this skill and can be moved: it passes the folder's own paths to the launcher at every start. `team.sh workspace <dir>` changes the project folder saved in `team.conf`. This skill is needed to create or upgrade a team.

## Rules

- Ask one question per message and wait for the answer. Offer the default or the value you already have, so the user can answer "yes".
- **Never read, print, copy, move or upload a key file** (`identity.key`) or anything else under the agents' root (default `~/.buzz-agents`). Never open, `cat`, `grep` or `head` an env file (`.env.buzz-acp.local`) or `settings.conf`. Use `agent-team.sh status` and `agent-team.sh settings` to see what exists.
- **Never sign in or out, and never read a credential or a Claude or Codex settings file** (`~/.claude`, `~/.codex`). The user signs in in their own terminal; the script's checks ask the CLIs how they are signed in, and the adapters use the sign-in themselves.
- Never run `buzz-admin generate-key` yourself, and never put a secret in a command line or a message. Public keys and ownership proofs are not secret; you may show them.
- Use only the commands and options in this file. When a command fails, stop, show its message, and help the user fix the cause. Never work around a refusal.
- `finish` without `--dry-run` contacts the community: run it only after the user has seen the dry run and said yes.
- `proof --force` only replaces a proof already stored for that agent; it skips no check. `proof --no-signature-check` skips only the signature check; use it only as step 10 says, with the user's go-ahead.
- **Agents are started with the team's own command, `team.sh` in the team folder, or with one agent's own `start.sh` in its agent folder, never with this skill's script.** `create` and `upgrade` put both there. Give the user that command for their own terminal; run it yourself only when they ask. Agents started with it keep running after this conversation.

## What the tool will ask the user to approve

Tell the user this right after the first preflight, before any command writes under `~/.buzz-agents`, in a sentence or two for the tool you are running in.

### Claude Code

- Each run of the script is a shell command. In the default permission mode, Claude Code asks before running shell commands other than a built-in read-only set; "Yes, and don't ask again" keeps that command allowed for this repository. Source: https://code.claude.com/docs/en/permissions ("Permission system").
- **Writing under `~/.buzz-agents`**, outside the workspace (`settings`, `create`, `proof`, `upgrade`, `models`, and the team command `team.sh`): with Claude Code's Bash sandbox off, which is the default, the command approval is all that is asked. With the sandbox on, sandboxed commands may write only in the working directory, a temporary folder and added directories: add the root with `/add-dir ~/.buzz-agents`, or allow it with `sandbox.filesystem.allowWrite`. Source: https://code.claude.com/docs/en/sandboxing ("Writes", "Filesystem isolation").
- **Network for `models` and `finish`**: `models` opens a session with the backend's adapter, which reaches the provider with the user's sign-in; `finish` contacts the community. With the sandbox on, Claude Code asks the first time a command needs a new domain. Source: https://code.claude.com/docs/en/sandboxing ("Network").
- **Background processes for `team.sh`**: Claude Code documents only the commands it puts in the background itself. `team.sh` returns after starting the agents, and whether they keep running after Claude Code ends is not documented. That is why the user starts them in their own terminal. Source: https://code.claude.com/docs/en/tools-reference ("Background commands").

### Codex

- Codex runs commands in a sandbox. In the default `workspace-write` mode it may write only in the workspace (the current folder and temporary folders such as `/tmp`), and it has no network. With the `on-request` approval policy, it asks the user before writing outside the workspace or using the network. Source: https://learn.chatgpt.com/docs/agent-approvals-security ("Defaults and recommendations", "Network access").
- **Writing under `~/.buzz-agents`** (`settings`, `create`, `proof`, `upgrade`, `models`, and the team command `team.sh`): Codex asks for approval, because the folder is outside the workspace. To avoid the question, the user can start Codex with `--add-dir ~/.buzz-agents` ("Additional directories that should be writable alongside the primary workspace", `codex --help`). Whether `--add-dir` accepts a folder that does not exist yet is not checked, so create it first with `mkdir -m 700 ~/.buzz-agents`.
- **Network for `models` and `finish`**: Codex asks to run them with network access, because the adapter reaches the provider and `finish` reaches the community. A permanent alternative is `sandbox_workspace_write.network_access = true` in the Codex configuration. Source: https://learn.chatgpt.com/docs/agent-approvals-security ("Network access").
- **Background processes for `team.sh`**: the agents need the network and must keep running. The Codex documentation does not say whether processes started by a command outlive the session; not checked. The user starts them in their own terminal.

## Flow

1. **Backends, then `agent-team.sh preflight`.** Ask: "Claude or Codex for the workspace agent and the channel supervisor: the same backend for both, or different?" Reuse a choice the user already gave. For an existing team, start with `status`; a team in format 1 or 2 goes through step 13 first.
   - **Sign-in, in the user's own terminal** (you never sign in): for Claude, `claude auth login`, choosing the Claude subscription (not Console), then `claude auth status --text`, which should say `Login method: Claude … account`. For Codex, `codex login`, choosing Sign in with ChatGPT, then `codex login status`, which should say `Logged in using ChatGPT`.
   - Codex also needs the tested adapter, `npm install -g --prefix "$HOME/.local" @agentclientprotocol/codex-acp@1.13.1`, and the channel supervisor's engine, `npm install --prefix "$HOME/.local/share/buzz-agent-team" --save-exact @openai/codex@0.171.0 @modelcontextprotocol/sdk@1.32.2 zod@4.6.7`. The user runs these in their own terminal.
   - Run `agent-team.sh preflight --backend <claude|codex>`, or `agent-team.sh preflight --agent-backend <b> --supervisor-backend <b>` for different backends. It checks each role's adapter, its runtime and its sign-in, and it fails when a Claude settings file or the Codex configuration would add an API key, token, helper or endpoint.
   - For each line marked `MISSING` or `PROBLEM`, take one at a time: say what is missing and ask for what fixes it.
     - Key generator: ask where `buzz-admin` is (in a Buzz checkout: `target/debug/buzz-admin`), then run `agent-team.sh settings --keygen <path>`.
     - Launcher: ask where the accepted `run-buzz-acp.sh` is, then run `agent-team.sh settings --launcher <path>`.
     - `buzz`, `buzz-acp`, `claude-agent-acp` or `codex-acp` not on `PATH`: the user adds the folder to `PATH` in their shell profile. If this session still does not see it, the user starts a new session from a new terminal.
     - A sign-in or settings problem: the fix line says what the user does in their own terminal or which entry to remove; names are shown, never values.
   - Run preflight again until it says "Preflight passed". Show the `Launcher:` line and ask the user to confirm it is the accepted launcher.
2. **Models.** For each chosen backend and role, run `agent-team.sh models --backend <b> --role <agent|supervisor>` and show the list. It opens one session with the adapter that role runs and makes no model turn. Ask: "Which model for the workspace agent, and which for the channel supervisor (or the same for both)? Enter keeps the runtime default." Offer `claude-opus-5-5` first for Claude only when the list shows it or shows Opus 5.5. Never offer `default` from a Claude list as a model: it is refused; no model at all means the runtime default. If the listing fails, show its reason and the documented list it printed instead.
   - **Reasoning effort (optional).** Ask: "A reasoning effort for each agent, or leave that to your own settings?" Higher levels think longer on every turn and use more of the subscription allowance; the channel supervisor takes a turn on every ordinary message, so say that a lower level suits it. On Claude the levels are `low`, `medium`, `high`, `xhigh` and `max`. On Codex they are the levels the model list shows for that model as `model[level]`, and a level needs a model. With none set, Claude Code uses the user's own saved level for that model, or the model's default, and Codex uses the default of the user's Codex configuration. Pass the answer to `create` or `upgrade` as `--agent-effort <level>`, `--supervisor-effort <level>`, `--reviewer-effort <level>`, or `--effort <level>` for all; `default` clears a saved one.
   - **The workspace agent's workers (optional).** Ask: "A model and a reasoning effort for the workspace agent's workers, the subagents it starts for bounded work, or the same as the agent?" On Claude the model is one of `opus`, `sonnet`, `haiku` and `fable`, the names its subagent tool takes when the agent starts a worker; on Codex offer the models of the list. The levels are the agent's (on Codex the ones the list has for that model). Pass the answer to `create` or `upgrade` as `--worker-model <name>` and `--worker-effort <level>`; they are saved for the workspace agent's backend in that run, and `default` clears a saved one.
     - Say how they are applied: at each start they are named in the agent's system prompt for that run, in a section at its end that asks it to pass them when it starts a worker. Nothing is written into the project folder and nothing is set for them. It is an instruction the agent is trusted to follow, not something enforced, on Claude and on Codex alike.
     - **On Claude** a level for the workers works only while the workspace agent has no level of its own, because Claude applies the level a session runs at to its workers whatever level the agent names; `create` and `upgrade` refuse to save both.
3. **Defaults.** Skip this step when preflight shows both `community` and `owner` as `ok`. Otherwise, one question per message:
   1. Ask: "Do you have a working `.env.buzz-acp.local` from an agent you already run? I can copy your community address, your public key and the model from it; nothing secret is copied." If yes, ask for its path.
   2. If there is no such file, ask for the community address (`wss://…`), then, in the next message, for the user's own public key (64 hex characters, not an npub).
   3. Ask whether to remember these values for next time.
      - Remember, from the file: run `agent-team.sh settings --from-env <file>`.
      - Remember, typed values: run `agent-team.sh settings --community <url> --owner <hex>`.
      - Do not remember: pass them to `create` in step 9, as `--from-env <file>` or as `--community <url> --owner <hex>`.
   4. After `settings`, show the values it printed. If `community` or `owner` is still `(not set)`, ask for it and store it the same way.
4. **Workspace.** Ask for the workspace folder (an absolute path).
5. **Channel.** Ask for the channel ID, a UUID. A copied message link `buzz://message?channel=<uuid>&id=…` contains it.
6. **Which agents.** Ask: "A workspace agent and a channel supervisor, or a workspace agent for a channel that already has a channel supervisor?" For a workspace agent only, use the existing channel supervisor’s display name (`--supervisor-name`); the workspace agent then answers it. An independent reviewer is a separate one-agent team: step 14.
7. **Names.** Say the default display names ("<Workspace>", "<Workspace> Supervisor") and ask whether to keep them.
8. **Brief.** Ask: "Anything the agents should know about this workspace? A few lines on what it is and what you want from them. You can leave it blank."
   - **Blank:** leave `--brief` out in step 9. The agents then learn about the workspace from its files and from the user's messages.
   - **With an answer:** add `--brief -` in step 9 and give the text on standard input, in a quoted here-document so it is taken literally:

     ```
     agent-team.sh create <the other options> --brief - <<'BRIEF'
     <the user's text>
     BRIEF
     ```
   - The brief goes at the end of each agent's prompt, marked as background and not as a task. It is kept in `brief.md` in the workspace's folder under the agents' root. At most 4000 characters; a key, a proof or a password never belongs in it.
9. **Create.** Run:
   `agent-team.sh create --workspace <folder> --channel <uuid> [--agent-backend <b>] [--supervisor-backend <b>] [--agent-model <id>] [--supervisor-model <id>] [--roles agent] [--agent-name "<name>"] [--supervisor-name "<name>"] [--brief -] [--from-env <file> | --community <url> --owner <hex>]`
   - Use `--backend <b>` instead of the two backend options when both roles use the same backend. A model the backend does not offer for that role is refused.
   - For a workspace agent on Claude, `create` first writes the sandbox settings into `<folder>/.claude/settings.json` and prints `Project folder settings: ...`. Before running it, tell the user that this file applies to every Claude Code session started in that folder, their own included.
   - Show the line that says whom the workspace agent answers. With `--roles agent` and no channel supervisor of that name on this machine, it answers the owner only.
   - If it says the workspace name is already used by another folder, ask for another name and run it again with `--name <name>`. For a new team, creation initializes `PROJECT.md` if the workspace lacks one. It preserves existing project records, role prompts and identities.
   - Remember the workspace name it printed: later commands take it as `<name>`.
10. **Proofs, one agent at a time.** `<agent>` is the agent's folder name, as the first column of the create output lists them: the team's name (or `agent`) for the workspace agent, `supervisor` for the channel supervisor.
    1. Show one agent's public key from the create output, and tell the user: in Buzz Desktop open Settings, then Security, then "Authorize external identity"; paste this public key and copy the proof it gives.
    2. Ask the user to paste the proof here.
    3. Run `printf '%s\n' '<proof>' | agent-team.sh proof <name> <agent> -` and show its check lines. Then do the next agent.
    - **If it is refused with `signature: FAILED`:** ask the user to confirm they pasted exactly that agent's public key, and to copy the proof again. If the same proof is refused again, the offline check may be wrong. With the user's go-ahead, store it with `printf '%s\n' '<proof>' | agent-team.sh proof <name> <agent> - --no-signature-check`. Then tell the user that the agent's first start is the first real check: if its `agent.log` shows `BUZZ_AUTH_TAG verification failed` or a relay connection error, or the agent never comes online, they copy a new proof, and you store it with `--force`.
    - **Any other refusal** (malformed, another owner, expired) means the user must copy a new proof. Neither option overrides it.
11. **How the agents join the channel.** Ask which way:
    - **`add`** (the default): the user adds them, signing through their Buzz desktop pairing. Ask whether they have paired the CLI with Buzz Desktop already. If not, they run `buzz --relay <community> auth desktop pair` in their own terminal and approve it in Buzz Desktop, then tell you it is done.
    - **`join`**: for an open channel; each agent joins itself.
    - **`skip`**: the user adds them in Buzz Desktop.

    The agents get the channel role `bot` unless the user wants `member`. Then run `agent-team.sh finish <name> --dry-run [--channel-step add|join|skip] [--role bot|member]`, show the commands, ask the user to confirm that no other member of the channel already uses these display names, and on yes run it without `--dry-run`. If a step fails, stop and report it; `finish` is safe to run again after the fix.
12. **Check and start, with the team's own command.** Give the user three commands for their own terminal, using the paths `create` or `upgrade` printed: `cd <workspace folder>`, then `~/.buzz-agents/<name>/team.sh check` (their terminal may differ from this session), then `~/.buzz-agents/<name>/team.sh`.
    - The agents work in the folder the command is run from, so the `cd` matters. `--workspace <dir>` names another folder for one run.
    - In a terminal, start asks which agents to start, then for each one its provider, its model and its reasoning effort. For the workspace agent it then asks two more questions: the model for its workers on that provider (on Claude `opus`, `sonnet`, `haiku` or `fable`), and their reasoning effort. On Claude, when the workspace agent has a level of its own for the run, the second is not asked: one line says the workers run at that level, and why. The model menu offers the list the provider's adapter gives at that moment, or the kept one when it cannot be reached. Enter keeps each saved choice, and a choice lasts for that run.
    - The same without questions: `team.sh start supervisor --backend codex`, `team.sh start --agent-model <id>`, `team.sh start --supervisor-effort high`, `team.sh start --worker-model <name> --worker-effort <level>` (the workspace agent's workers, for one run; `default` means none), `team.sh start --yes` (every saved choice). The worker options are refused when the workspace agent is not started, and on Claude `--worker-effort` is refused beside a level of the agent's own: then start it with `--effort default`.
    - The workers' choices go into the agent's system prompt for that run only: `prompt.run.md` in its folder, its `prompt.md` followed by a section "Your workers for this run". `prompt.md` itself is not changed.
    - One agent at a time: `~/.buzz-agents/<name>/<agent>/start.sh`, with `<agent>` the agent's folder (for a team called `shop`: `~/.buzz-agents/shop/shop/start.sh` and `~/.buzz-agents/shop/supervisor/start.sh`), run from the project folder like the team command. It starts that agent only, asking its provider, model and effort in a terminal; `start.sh --yes` asks nothing and keeps the saved choices. A reviewer's team has its own: `~/.buzz-agents/<name>-reviewer/reviewer/start.sh`. Starting one team's agents starts no other team.
    - Starting an agent that already runs on another provider stops with a message: stop it first with `team.sh stop <agent>`.
    - Each agent writes `agent.log` in its folder. `team.sh status` shows each agent's saved provider and model and what runs now; `team.sh stop` stops them.
    - Before the first start in a project folder, `team.sh` puts the workspace agent's sandbox settings into `<project folder>/.claude/settings.json` and prints the file's path. `team.sh check` names the file, or says that a start will write it. A settings file that is not valid JSON stops the start with the reason; the user fixes or removes it.
    - The workspace agent on Claude runs a tool installed under the user's home folder outside the sandbox, which its prompt allows for that purpose. If the user wants no sandbox settings in a folder, `team.sh start --no-wall` starts the workspace agent there with only the rule in its prompt, and the user decides that. Settings that are already in the folder stay and apply; the user removes them from `.claude/settings.json` by hand.
    - Run `team.sh` yourself only if the user asks. Do not use `agent-team.sh start` for this: it still exists and shares the same `agent.pid` and `agent.log`, but the team's own command is the one to give the user.
    - For a smoke test, have a channel member ask an ordinary question; the channel supervisor's useful reply or silence is valid. Ask the owner to mention the workspace agent for a catch-up.
13. **Upgrade an existing team** (a team in format 1, 2 or 3, or to change a saved backend or model). Agents must be stopped. Run `agent-team.sh upgrade <name> --dry-run [--backend <b> | --agent-backend <b> --supervisor-backend <b>] [--agent-model <id>] [--supervisor-model <id>] [--worker-model <name>] [--worker-effort <level>]` and show the plan: which files it replaces (each kept beside itself as `<file>.bak-<time>`), which settings are not carried over (names only), and that keys, proofs and `PROJECT.md` stay unchanged.
